# Contributor Recognition

ContributorOps is built in public, and useful contributions should remain visible.

## How contributors are recognized

- GitHub commit and pull-request attribution remains the primary source of contribution history.
- Merged external pull requests should be acknowledged in release notes or meaningful project updates when releases are published.
- Documentation, accessibility, testing, design, issue triage, and architecture contributions count alongside feature code.
- Substantial architecture changes should preserve contributor authorship in the relevant ADR or pull request discussion.

## Current contributor history

The project intentionally avoids maintaining a manually ranked leaderboard because contribution quality, review effort, documentation, testing, and maintainer impact are not comparable through commit counts alone.

## What earns recognition

Examples include:
- focused feature or bug-fix pull requests
- regression tests around the approval/safety boundary
- accessibility and developer-experience improvements
- documentation that materially improves onboarding or architecture clarity
- useful issue reports with reproducible evidence
- review feedback that changes implementation quality

## What does not count as meaningful recognition signal

- automated commit volume
- mass-generated low-context pull requests
- superficial documentation churn
- contribution activity that bypasses project safety rules

See [`CONTRIBUTING.md`](./CONTRIBUTING.md) for the contribution workflow and [`docs/safety-policy.md`](./docs/safety-policy.md) for non-negotiable external-write constraints.
